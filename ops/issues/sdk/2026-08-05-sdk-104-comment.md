### Nachverifiziert gegen 4.7.3-local.202608032047 — unverändert blockiert

Aufgekommen erneut bei der Callora-Audit-Remediation (BechsteinDigital/callora#111, das
IP-authentifizierte und mutual-TLS-Accounts fordert). Der Befund von damals gilt weiterhin,
hier die Belege aus der aktuellen Assembly:

- `CalloraVoipSdk.Core.Domain.Lines.SipAccount` trägt weiterhin nur
  `DisplayName`, `Username`, `Password`, `SipServer`, `Transport`, `Port`,
  `RegistrationExpiry`, `OutboundProxy`, `PublicSipHost`, `PublicSipPort`,
  `PublicMediaHost`, `InboundNumbers`, `AcceptTrunkInbound`, `Reregister` — kein Schalter
  für „nicht registrieren".
- `SipLineChannel.CreateRegistrationRequest` setzt `ExpiresSeconds` auf
  `Math.Max(1, account.RegistrationExpiry)`. Ein `RegistrationExpiry` von 0 schaltet die
  Registrierung also **nicht** ab, sondern erzeugt eine 1-Sekunden-Registrierung.
- Es gibt keinen Verbindungspfad an `SipLineChannel.RegisterAsync` vorbei.

### Auswirkung auf Callora (jetzt konkret)

Callora modelliert `SipAccountMode.Trunk` + `IpAuthentication` in Domäne, API und Admin-UI.
Ohne SDK-Unterstützung wird ein solcher Account angelegt, beim Provisionieren aber
übersprungen — die UI bleibt auf `Connecting` stehen. Callora schließt das jetzt fail-closed:
die Anlage wird mit 422 abgelehnt und der Account-Typ verschwindet aus der UI, bis dieses
Issue umgesetzt ist. Sobald das SDK den Modus trägt, wird die Ablehnung entfernt.

### Priorisierungs-Argument

Das Issue ist als P3/optional geführt, weil der Massenmarkt registrierend ist. Das stimmt
weiterhin. Es ist jetzt aber der einzige Grund, warum Callora einen dokumentierten
Account-Typ zurückbauen muss — falls IP-authentifizierte Trunks im Zielmarkt vorkommen
sollen, wäre eine Höherstufung sinnvoll.
